# 基础设施服务

本文记录 SociLab 后续业务可使用的基础设施、环境变量和建议接入边界。当前仓库只实现配置读取与校验，没有安装 SDK、创建连接或实现任何业务调用。

## 配置装配原则

- Server 网络配置始终启用，未配置时监听 `127.0.0.1:4317`
- PostgreSQL、Redis、OSS、短信、邮件和 Cap 都是独立可选配置组
- 一组变量全部为空时对应配置为 `undefined`；填写任一字段后必须通过整组校验
- 端口必须是 `1–65535` 的整数
- AccessKey、密码和 secret key 只允许进入 Server 环境，不得写入 `VITE_*`、日志或错误响应
- `.env.example` 只提供字段和安全占位值，真实环境文件不进入 Git

完整字段以 [`projects/server/.env.example`](../projects/server/.env.example) 为准。

## PostgreSQL

| 配置 | 用途 | 默认值 |
| --- | --- | --- |
| `DATABASE_HOST` | 数据库主机 | `localhost` |
| `DATABASE_PORT` | 数据库端口 | `5432` |
| `DATABASE_USER` | 应用数据库用户 | 无 |
| `DATABASE_PASSWORD` | 应用数据库密码 | 无 |
| `DATABASE_NAME` | 应用数据库名称 | 无 |

后续建议沿用 qygent 的 Drizzle Schema、迁移和 Repository 组织原则，并针对 PostgreSQL 使用 `drizzle-orm` 与 `pg`。Drizzle 同时支持 `node-postgres` 和 `postgres.js`；SociLab 优先选择 `pg` 的连接池，以便显式管理进程级连接、事务和关闭流程。

数据库连接应由 Server 的具体持久化能力拥有：启动时建池并验证连接，关闭时等待在途事务后释放。HTTP handler 不直接创建连接，不在 API 契约中暴露数据库模型。迁移只在明确建立首个持久化业务模块时加入，不预建空 Schema。

参考：[Drizzle PostgreSQL 接入](https://orm.drizzle.team/docs/get-started-postgresql)

## Redis

| 配置 | 用途 | 默认值 |
| --- | --- | --- |
| `REDIS_HOST` | Redis 主机 | `localhost` |
| `REDIS_PORT` | Redis 端口 | `6379` |
| `REDIS_USER` | 可选 ACL 用户 | 无 |
| `REDIS_PASSWORD` | 可选密码 | 无 |

整个 Redis 服务供 SociLab 业务使用，环境变量只描述服务连接，不指定单一 DB。业务能力从 DB0 开始按实际落地顺序分配可用逻辑 DB，并在服务端代码中集中登记用途；同时使用稳定的领域 key 前缀，避免仅依赖 DB 编号形成隐式所有权。DB 分配应在首个真实调用方出现时记录，不提前占用编号，也不允许部署配置改变业务数据所有权。

后续使用官方推荐的 `redis` 包（node-redis）。连接由 Server 进程级基础设施持有，注册 `error` 监听并在关闭阶段主动释放；业务模块只获取收窄后的缓存、限流或一次性令牌接口，不共享可任意执行命令的全局客户端。

参考：[Redis Node.js 客户端](https://redis.io/docs/latest/develop/clients/nodejs/)、[node-redis 错误处理](https://redis.io/docs/latest/develop/clients/nodejs/error-handling/)

## 阿里云 OSS

| 配置 | 用途 | 默认值 |
| --- | --- | --- |
| `OSS_ACCESS_KEY_ID` | RAM AccessKey ID | 无 |
| `OSS_ACCESS_KEY_SECRET` | RAM AccessKey Secret | 无 |
| `OSS_REGION` | OSS region，例如 `oss-cn-hangzhou` | 无 |
| `OSS_ENDPOINT` | 可选公网、内网或自定义 endpoint | 无 |
| `OSS_SECURE` | 是否使用 HTTPS | `true` |
| `OSS_BUCKET_PUBLIC` | 已开启公共读的公共存储桶 | 无 |
| `OSS_BUCKET_PRIVATE` | 私有存储桶 | 无 |

后续使用官方 `ali-oss` Node.js SDK，并启用 Signature V4。RAM 身份只授予两个目标桶所需的最小读写权限，不使用阿里云主账号 AccessKey。

- 公共桶用于确实允许匿名读取的资源；上传、删除和覆盖仍只经 Server 授权
- 私有桶保持私有，通过短时签名 URL 或 Server 流式响应提供受控下载
- 应用不自动修改 Bucket ACL，公共读状态由基础设施侧预先配置并审计
- 同地域部署时可通过 `OSS_ENDPOINT` 选择内网 endpoint，外部部署使用公网 endpoint

参考：[阿里云 OSS Node.js SDK](https://help.aliyun.com/en/oss/developer-reference/nodejs-sdk/)、[OSS Endpoint 规则](https://help.aliyun.com/en/oss/developer-reference/overview-24)

## 阿里云短信

| 配置 | 用途 | 默认值 |
| --- | --- | --- |
| `SMS_ACCESS_KEY_ID` | RAM AccessKey ID | 无 |
| `SMS_ACCESS_KEY_SECRET` | RAM AccessKey Secret | 无 |
| `SMS_REGION` | 短信服务 region | `cn-hangzhou` |
| `SMS_SIGN_NAME` | 审核通过的签名名称 | 无 |
| `SMS_CODE_TEMPLATE_CODE` | 审核通过的验证码模板 CODE | 无 |

后续使用阿里云官方 `@alicloud/dysmsapi20170525` TypeScript SDK，只允许 Server 调用。签名与模板 CODE 必须和控制台审核通过的值完全一致，AccessKey 使用最小权限 RAM 身份。

发送短信是计费且不提供业务幂等保证的外部操作。业务落地时必须先建立验证码记录和发送幂等键，再调用供应商；超时后查询发送结果或按明确策略补偿，不能直接无条件重试造成重复短信。

参考：[阿里云短信 TypeScript SDK](https://help.aliyun.com/zh/sms/developer-reference/using-typescript-openapi-example)、[SendSms 接口](https://help.aliyun.com/zh/sms/developer-reference/api-dysmsapi-2017-05-25-sendsms)

## 飞书邮箱

| 配置 | 用途 | 默认值 |
| --- | --- | --- |
| `EMAIL_HOST` | SMTP 主机 | 无 |
| `EMAIL_PORT` | SMTP 端口 | `465` |
| `EMAIL_USER` | 发件邮箱地址 | 无 |
| `EMAIL_PASSWORD` | 飞书邮箱客户端专用密码 | 无 |
| `EMAIL_SECURE` | 是否建立安全连接 | `true` |
| `EMAIL_RATE_LIMIT_PER_SECOND` | 每秒发送上限 | `2` |

飞书管理员需要先允许第三方邮箱客户端登录，再由成员生成客户端专用密码。飞书邮箱没有供应用直接使用的普通登录密码；SMTP host、port 与安全方式以企业后台实际展示的客户端参数为准，不在源码中硬编码供应商地址。

后续使用 `nodemailer` 的 SMTP transport，创建单个进程级 transporter，并在启动时执行连接验证。业务调用先经过统一邮件服务执行模板渲染、收件人校验、频率限制和敏感信息清理；需要队列时再建立真实队列边界。

参考：[飞书邮箱第三方客户端设置](https://www.feishu.cn/hc/zh-CN/articles/360049068017//)、[Nodemailer SMTP transport](https://nodemailer.com/smtp)

## 自托管 Cap 验证码

| 配置 | 用途 | 默认值 |
| --- | --- | --- |
| `CAPTCHA_SERVER_ENDPOINT` | Server 访问的 Cap 地址 | 无 |
| `CAPTCHA_CLIENT_ENDPOINT` | 浏览器访问的 Cap 公共地址 | 无 |
| `CAPTCHA_SITE_KEY` | Cap site key | 无 |
| `CAPTCHA_SECRET_KEY` | Server 验证 token 的 secret key | 无 |

后续 Client/Admin 使用 `cap-widget` 的 programmatic mode，在提交登录、注册、找回密码等受保护动作前调用 `solve()`，不显示常驻验证码控件。浏览器只接收公共 endpoint 与 site key，secret key 永远留在 Server。

Server 接收浏览器生成的 token 后，向 `${CAPTCHA_SERVER_ENDPOINT}/${CAPTCHA_SITE_KEY}/siteverify` 发送 `secret` 与 `response`。验证成功后立即执行业务动作；token 是单次使用凭据，不能缓存、复用或写入日志。公共 endpoint 与 site key 后续通过公共技术配置契约下发，不在两个 Web 应用复制静态配置。

参考：[Cap programmatic mode](https://capjs.js.org/guide/programmatic.html)、[Cap 服务端验证](https://capjs.js.org/guide/)

## 后续落地顺序

1. 业务模块先定义真实数据所有权、失败边界和接口契约
2. 只为该业务引入所需 SDK，并在 `projects/server/src/infra` 建立具体连接所有者
3. 在模块入口注入收窄后的能力，不让 handler 直接读取 `process.env` 或创建客户端
4. 使用内存替身完成单元测试，再以独立测试环境验证真实服务
5. 将连接检查、超时、重试、幂等、关闭和敏感日志规则纳入对应领域测试
